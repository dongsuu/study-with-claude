실행 컨텍스트 심화: 바인딩이 생기고 채워지는 순간

1편(실행 컨텍스트와 TDZ)에서 결론만 다뤘던 내용을, 엔진이 실제로 하는 동작 단위로 쪼개서 봅니다. 이 페이지를 읽고 나면 "호이스팅"이라는 단어 없이도 모든 결과를 설명할 수 있어야 합니다.

01큰 그림: 코드는 3단계를 거쳐 실행된다

Stage 1파싱코드 전체를 읽고 구조를 파악합니다. 어떤 스코프에 어떤 선언이 있는지 이 시점에 이미 다 압니다. 문법 오류가 있으면 한 줄도 실행되지 않습니다.
Stage 2선언 단계실행 컨텍스트를 만들고, 그 스코프의 선언들을 Environment Record에 등록합니다. 스펙 용어로 선언 인스턴스화(Declaration Instantiation)입니다.
Stage 3실행 단계코드를 위에서부터 한 줄씩 평가합니다. 값을 계산하고, 할당하고, 함수를 호출합니다.

Stage 2와 3은 스코프마다 반복됩니다. 전역 코드가 시작될 때 한 번, 함수가 호출될 때마다 한 번, 블록 { }에 들어갈 때마다 한 번(블록 안에 let/const/class가 있을 때)씩 일어납니다.

"호이스팅"은 Stage 2에서 일어난 일을 Stage 3에서 관찰했을 때 마치 선언이 위로 올라간 것처럼 보이는 현상에 붙인 별명일 뿐입니다. 스펙에는 hoisting이라는 동작이 없습니다.

console.log('첫 줄');
let a = 1;
let a = 2; // 같은 스코프에 let 중복
결과 보기
SyntaxError: Identifier 'a' has already been declared'첫 줄'조차 출력되지 않습니다. 파싱(Stage 1)에서 실패했기 때문에 실행 단계에 들어가지도 못합니다.

02용어 정리: 선언 · 바인딩 · 초기화 · 할당

이 네 단어를 구분하지 못하면 모든 설명이 흐려집니다. 일상에서는 섞어 쓰지만, 엔진 입장에서는 전혀 다른 동작입니다.

용어뜻엔진 입장에서
선언소스 코드에 적힌 var x, let x, function f(){} 같은 문법 요소파싱 때 발견되어 "이 스코프에는 x가 있다"는 정보가 됨
바인딩Environment Record 안에 있는 이름 → 값 슬롯 하나슬롯마다 "초기화됐는가", "바꿀 수 있는가(const 여부)" 상태를 가짐
초기화바인딩에 첫 값을 넣는 것. 바인딩마다 딱 한 번스펙의 InitializeBinding. 이것이 일어나야 읽고 쓸 수 있음
할당이미 초기화된 바인딩의 값을 바꾸는 것. x = 1스펙의 SetMutableBinding. 초기화 전이면 에러, const면 에러

바인딩의 상태 변화

없음Environment Record에 이름이 없음
생성
Create…Binding
미초기화 (TDZ)슬롯은 있지만 값이 없음. 읽기·쓰기 모두 ReferenceError
초기화
InitializeBinding
초기화됨값이 있음. 이후 할당으로 값 변경 가능 (const 제외)

var와 function 선언은 선언 단계에서 생성과 초기화가 한 번에 일어나서 미초기화 상태를 거치지 않습니다. let/const/class만 미초기화 상태로 머물며, 그 구간이 TDZ입니다.

핵심. var x = 1;에서 = 1은 초기화가 아니라 할당입니다. x는 선언 단계에서 이미 undefined로 초기화되었기 때문입니다. 반면 let x = 1;의 = 1은 진짜 초기화입니다. 같은 모양의 코드가 다른 동작을 합니다.

03선언문 하나는 두 번 일한다

선언문 한 줄은 선언 단계와 실행 단계에 걸쳐 두 번 처리됩니다. 각 단계에서 무슨 일이 일어나는지 나눠 보면, 결과를 외울 필요가 없어집니다.

코드선언 단계 (Stage 2)실행 단계 (Stage 3, 그 줄에 도달했을 때)
var x = 1;바인딩 생성 + undefined로 초기화CreateMutableBinding + InitializeBinding(undefined)1을 할당SetMutableBinding(x, 1)
var x;위와 같음아무 일도 안 함 (값을 undefined로 되돌리지 않음)
let x = 1;바인딩 생성만CreateMutableBinding1로 초기화 → 여기서 TDZ 끝InitializeBinding(x, 1)
let x;바인딩 생성만undefined로 초기화
const x = 1;변경 불가 바인딩 생성만CreateImmutableBinding1로 초기화 (const x;는 파싱 단계 SyntaxError)
function f() {}바인딩 생성 + 함수 객체를 만들어서 초기화. 이때 f.[[Environment]] = 현재 환경InstantiateFunctionObject아무 일도 안 함 (건너뜀)
var f = function () {};var 규칙: undefined로 초기화이 줄에서 함수 객체가 처음 만들어지고 할당됨
class C {}바인딩 생성만 (let과 같음)클래스 객체를 만들어 초기화

표의 함수 선언 행이 중요합니다. 함수 선언은 선언 단계에서 본문까지 완성된 함수 객체가 만들어집니다. "빈 함수가 먼저 들어가고 나중에 구현이 채워진다" 같은 중간 상태는 없습니다. 실행 단계에서 function f() {} 줄은 이미 처리된 줄로 보고 건너뜁니다.

05선언 인스턴스화의 순서

선언 단계 안에서도 처리 순서가 정해져 있습니다. 스펙(FunctionDeclarationInstantiation)을 학습용으로 단순화하면 이렇습니다.

함수가 호출될 때

  1. 매개변수 바인딩을 만들고 전달된 인자로 초기화합니다. 기본값이 있으면 왼쪽부터 하나씩 평가하며 초기화하므로, 아직 차례가 오지 않은 오른쪽 매개변수는 TDZ 상태입니다.
  2. 일반 함수라면 arguments 객체를 만듭니다. (화살표 함수는 없음)
  3. var 선언을 처리합니다. 같은 이름의 바인딩이 이미 있으면 건너뛰고, 없으면 만들어서 undefined로 초기화합니다.
  4. function 선언을 처리합니다. 함수 객체를 만들어 바인딩에 넣습니다. 이미 같은 이름이 있으면 값을 덮어씁니다.
  5. let / const / class 바인딩을 만듭니다. 초기화는 하지 않습니다.

3번과 4번의 규칙("var는 있으면 건너뜀, function은 덮어씀") 덕분에, 같은 이름의 var와 function이 있으면 소스상 순서와 관계없이 선언 단계가 끝난 시점의 값은 항상 함수입니다. 그다음 실행 단계에서 할당문을 만나야 비로소 다른 값으로 바뀝니다.

전역 코드가 시작될 때

함수와 거의 같지만, 먼저 충돌 검사를 합니다. let/const로 선언하려는 이름이 이미 전역에 있으면(다른 <script>에서 선언됐더라도) 그 스크립트는 코드를 하나도 실행하지 않고 SyntaxError로 끝납니다.

블록에 들어갈 때

블록 { }에 진입하면 새 Declarative Environment Record가 만들어지고, [[OuterEnv]]는 블록을 감싼 환경을 가리킵니다. 블록 안의 let/const/class는 이 레코드에 미초기화 상태로 생성됩니다. 블록에는 새 실행 컨텍스트가 생기지 않고, 현재 실행 컨텍스트의 LexicalEnvironment만 잠시 이 레코드로 바뀌었다가 블록을 나가면 되돌아갑니다. var는 블록을 무시하고 가장 가까운 함수(또는 전역) 레코드에 등록됩니다.

function demo() {
  // demo의 Function ER: { flag: undefined }  ← var는 블록 밖 함수 레코드로
  {
    // 블록 ER: { inBlock: <uninitialized> }, [[OuterEnv]] → demo ER
    let inBlock = 1;
    var flag = true;
  }
  // 블록 ER은 사라지고 LexicalEnvironment가 demo ER로 복귀
  return flag;
}

06읽기 · 쓰기 · typeof 규칙

실행 단계에서 식별자를 사용할 때 엔진은 먼저 현재 LexicalEnvironment부터 [[OuterEnv]]를 따라 올라가며 그 이름의 바인딩을 찾습니다(ResolveBinding). 가장 먼저 찾은 바인딩 하나만 사용하고, 그 바인딩이 미초기화 상태라도 더 바깥을 찾지 않습니다. 이것이 shadowing과 TDZ가 만나는 지점입니다.

sloppy: 전역 객체에 프로퍼티 생성		'undefined' (에러 아님)
찾았는데 미초기화 (TDZ)ReferenceError
Cannot access 'x' before initialization		ReferenceError (같은 메시지)ReferenceError
찾았고 초기화됨 (let/var)값그 바인딩의 값이 바뀜값의 타입

두 ReferenceError의 메시지가 다르다는 점은 엔진이 "바인딩이 없다"와 "바인딩은 있는데 초기화 전이다"를 구분한다는 뜻입니다. 쓰기는 바인딩을 찾은 레코드의 값을 바꾸며, 현재 레코드에 새 바인딩을 만들지 않습니다.

07흔한 오해 정리

호이스팅은 선언을 코드 맨 위로 옮기는 것
코드는 그대로이고, 선언 단계에서 바인딩이 먼저 등록될 뿐이다
let/const는 호이스팅되지 않는다
바인딩은 스코프 시작 시점에 생성된다. 초기화만 늦다
초기화되기 전 변수는 undefined다
var만 선언 단계에서 undefined로 초기화된다. let/const/class와 매개변수는 초기화 전에 접근하면 ReferenceError다
함수 선언은 빈 함수로 먼저 들어가고, 실행 단계에서 구현이 채워진다
선언 단계에서 완성된 함수 객체로 초기화된다. 실행 단계에서 그 줄은 건너뛴다
var x = 1의 = 1은 초기화다
이미 undefined로 초기화된 바인딩에 대한 할당이다
TDZ는 선언문보다 위에 있는 코드 영역이다
TDZ는 시간 구간이다. 선언문보다 위에 적힌 함수라도 선언문 실행 후에 호출되면 문제없다
실행 컨텍스트는 함수를 정의할 때 만들어진다
호출할 때마다 새로 만들어진다. 정의할 때는 [[Environment]]만 저장된다
